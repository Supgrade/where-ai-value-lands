why fully autonomous AI isn't here yet — even when the layers are

The model can do it. Layer 4 is why you don't let it.

The AI-first company loop has five layers. Four are technically achievable for a solopreneur today. Layer 4 — the gate that decides which agent action runs and which waits for you — is where the operator's name, reputation, and relationships sit on the table. Most loops have no Layer 4 at all. The few that do have one with a single setting: tight.

03 / 05 Build

In practice it isn't one slider — it's N sliders, one per action class.

A snapshot after the loop has been running for ~90 days. Some classes have ratcheted nearly all the way right; others sit one notch in; the irreversibles are pinned tight by policy. Every successful approved execution loosens the class by one notch. Every rollback resets it to zero.

The blocker is not the model. It's that every action carries your name.

Solopreneurs and operator-builders sit on a single reputational surface. Layer 4 — done as hooks + per-action-class ratchet + a verification GUI — is what lets the loop self-improve instead of paying the operator's attention back as supervision.

04 / 05 Ship

Give this to your agent. Two paths, both work today.

There is no off-the-shelf "trust-graduating gate" — you build it. Two concrete on-ramps for an operator-builder running Claude Code: a hook in .claude/settings.json that intercepts actions before they fire, or a sibling skill that maintains the trust ledger every other skill reads from.

1 drop into CLAUDE.md

Teach the agent the ratchet, in plain English.

place: project root · CLAUDE.md

The agent has to know the ratchet exists and where the trust ledger lives. One paragraph in CLAUDE.md gives every skill in the project the same shared discipline — no per-skill prompt drift.

# Autonomy ledger

You maintain .autonomy.yaml at the project root. Each
action class has a trust level 0–10 and an
irreversible flag.

Before any action of a tracked class:
  1. read .autonomy.yaml
  2. if irreversible: true → surface diff,
     wait for explicit approval, never auto-loosen
  3. else if trust < threshold → surface diff,
     wait for approval
  4. else → run, then log the action

After every approved success, increment trust
by 1. After any rollback, reset to 0 and add
a note explaining why.

The threshold drops by 1 every 5 approvals.
It never drops below 1 on action classes
marked external: true.

↳ this is the policy. the hook below is the enforcement.

2 add a PreToolUse hook

Enforce it deterministically — at the tool boundary.

place: .claude/settings.json

A PreToolUse hook intercepts every tool call before the model can run it. Classify the pending action, look up the trust level, exit non-zero if the action needs approval. The model cannot route around an exit code.

"hooks": {
  "PreToolUse": [
    {
      "matcher": "Bash|WebFetch|mcp__.*",
      "hooks": [
        {
          "type": "command",
          "command": "./.claude/gate.sh"
        }
      ]
    }
  ],
  "PostToolUse": [
    {
      "matcher": "Bash|mcp__.*",
      "hooks": [
        { "type": "command",
          "command": "./.claude/ratchet.sh" }
      ]
    }
  ]
}

↳ gate.sh reads .autonomy.yaml, blocks on under-threshold actions. ratchet.sh increments trust on success.

3 ship a /ratchet skill

Make the ledger a first-class operating surface.

place: .claude/skills/ratchet/SKILL.md

A slider buried in YAML is a slider that won't be tuned. Wrap the ledger in a slash command so you can see, at a glance, where each action class sits — and dial one back to "ask every step" the moment something goes sideways.

---
name: ratchet
description: inspect and tune the
  per-action-class autonomy ledger.
  use to view current trust levels,
  re-tighten after an incident, or
  mark a class as irreversible.
---

Read .autonomy.yaml. Print one row per class:
class · trust · threshold · irreversible · last
incident. Highlight any class within 1 of its
threshold in orange.

On /ratchet tighten <class> → reset trust to 0.
On /ratchet lock <class> → set irreversible.
On /ratchet review → show classes that
auto-loosened in the last 7 days, with diffs.

↳ this is the GUI. without it you won't look — and an untuned slider is a maximum-tight slider.

× what not to do

Loose by default. Tight forever. Verification as JSON.

three failure modes you'll watch other founders hit

A new action class deployed at "run on rails" gives one good morning and one career-defining mistake. A class pinned forever to "ask every step" means you supervised, you did not delegate — the surplus paid back as time. A verification surface that surfaces raw model output as JSON keeps review-cost high enough that the ratchet never trips.

↳ the discipline: start tight · loosen with evidence · keep one class of actions permanently locked · build the GUI you'd want to use.

Honest tensions — where this argument bends, and where it breaks.

The page is a working hypothesis under an open inquiry, not a sales pitch for an architecture.

no turnkey ratchet exists

As of 2026 the auto-ratchet has to be hand-built per harness — there is no off-the-shelf "trust-graduating gate" component. The page's prescription is directional. Expect this to become a surviving middle-layer primitive over the next 24 months; until then, the operator pays the build cost.

hooks can become bureaucracy

A loop with too many pre-action hooks degrades into the SaaS-approval-workflow pattern the loop was built to escape. Attach hooks where personal-liability exposure is non-trivial; remove them when post-action audit suffices. The discipline is subtractive.

straight-shot beats iron man?

Sutskever's "straight-shot" posture treats partial autonomy as the slow market-iterative path he is willing to abandon when capability is sufficient. If he is right, the architecture in this page is transitional, not durable. The wiki treats this as unresolved.

verification surface is undervalued capital

Most operator-builders treat the GUI layer as cosmetic. It isn't — it is the difference between a slider that ratchets and one that doesn't, and therefore between captured and uncaptured surplus. A slider buried in a YAML file is a slider that won't be tuned.
